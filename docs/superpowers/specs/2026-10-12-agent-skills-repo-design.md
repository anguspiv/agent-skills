# agent-skills — repository design

Date: 2026-10-12 · Status: accepted

## Goal

One public GitHub repository, `anguspiv/agent-skills`, that holds skills for
AI coding agents and serves them to two consumers from the same files:

- **Claude Code plugin marketplace** — `claude plugin marketplace add anguspiv/agent-skills`
- **skills.sh** — `npx skills add anguspiv/agent-skills`

Skills are versioned, released publicly, and managed with scripts that need
nothing beyond Node 22 and git.

## Non-goals

- Hooks, agents, MCP servers, or other non-skill plugin components. The
  layout allows them later; nothing here depends on them.
- Submission to Anthropic's directory. That is a manual portal step the
  owner does when a skill is ready. The repo keeps the metadata it needs.
- A documentation framework. Pages is a generated index, nothing more.

## Layout

```
skills/<name>/SKILL.md          hand-written; name == directory name
skills/<name>/{scripts,references,assets}/   optional, per agentskills spec
.claude-plugin/marketplace.json generated by scripts/catalog.mjs
.claude-plugin/plugin.json      generated; version owned by release-please
scripts/new.mjs                 scaffold a skill from a template
scripts/validate.mjs            frontmatter + layout checks, exits 1 on error
scripts/catalog.mjs             regenerate plugin.json, marketplace.json,
                                README skill table, docs/index.html
scripts/package.mjs             zip the plugin and each skill into dist/
scripts/lib/                    shared, unit-tested with node --test
.github/workflows/ci.yml        validate + catalog drift + tests on PR/push
.github/workflows/release.yml   release-please + release assets on main
.github/workflows/pages.yml     build docs/ and deploy to GitHub Pages
.github/ISSUE_TEMPLATE/         bug, skill-request, idea (forms)
.github/pull_request_template.md
docs/ideas.md                   backlog of skill ideas, one section each
docs/contributing.md            how to add a skill, run checks, release
```

## Both consumers, one source of truth

| consumer | reads | from |
| --- | --- | --- |
| skills.sh | `skills/*/SKILL.md` | scans `skills/` up to three levels deep |
| Claude Code | `.claude-plugin/marketplace.json` → entry `source: "./"` → `skills/` | default plugin layout, plugin root is the repo root |

One marketplace, one plugin to start:

```json
{
  "name": "anguspiv-skills",
  "owner": { "name": "Angus Perkerson", "url": "https://github.com/anguspiv" },
  "plugins": [
    { "name": "anguspiv-skills", "source": "./", "description": "..." }
  ]
}
```

Entry name equals manifest name (the docs call this out as the most common
install failure). Splitting into several plugins later means adding entries
whose `skills` field lists specific subdirectories and adding a `renames`
map; the generator owns both files so that is a script change.

The plugin name avoids the reserved prefixes (`claude-`, `anthropic-`).

## SKILL.md contract

Frontmatter per the agentskills specification, validated by `validate.mjs`:

- `name`: 1–64 chars, `[a-z0-9-]`, no leading/trailing/double hyphen,
  equal to the directory name
- `description`: 1–1024 chars, third person, says when to use it
- `license`: `MIT` (default from template)
- `metadata.version`: semver string, bumped by the author or by
  `catalog.mjs --bump <skill> <patch|minor|major>`
- `metadata.author`: `anguspiv`
- optional `compatibility`, `allowed-tools`

Body follows the writing-skills shape: overview, when to use, quick
reference, common mistakes. The template carries that skeleton.

## Versioning and releases

Two version lines, deliberately:

1. **Plugin version** (`plugin.json`): what Claude Code compares to decide
   whether a user gets an update. Owned by release-please. Conventional
   commits on `main` open a release PR; merging it bumps the version, writes
   `CHANGELOG.md`, tags `v<version>`, and creates a GitHub Release.
2. **Skill version** (`metadata.version` in each SKILL.md): a per-skill
   changelog marker for skills.sh users and for humans. CI fails when a
   skill's files changed since the last tag and its version did not.

Release assets, built by `package.mjs` in the release workflow:

- `anguspiv-skills-<version>.zip` — the plugin, loadable with
  `claude --plugin-url <asset url>`
- `<skill>-<skill-version>.skill` — one zip per skill, the format the
  Claude app accepts for "Save skill"

Commit scopes are skill names (`feat(commit-messages): ...`) so the
changelog groups by skill.

## CI

`ci.yml` on pull requests and pushes to `main`:

1. `node scripts/validate.mjs` — frontmatter, layout, stale skill versions
2. `node scripts/catalog.mjs --check` — generated files match sources
3. `node --test scripts/lib` — unit tests for the parsers and generators
4. `npx -y @anthropic-ai/claude-code plugin validate --strict .` — the
   authoritative marketplace and manifest check
5. PR title must be a conventional commit (amannn/action-semantic-pull-request)

Squash merge is the repo's merge method so PR titles become commit subjects.

## Pages

`pages.yml` runs `catalog.mjs` and deploys `docs/` with
`actions/deploy-pages`. `docs/index.html` is generated: one card per skill
with name, description, version, and both install commands. No framework,
no build dependency.

## Issues and Discussions

- Issue forms: `bug.yml` (which skill, which agent, what happened),
  `skill-request.yml` (problem, trigger phrases, expected behaviour),
  `idea.yml` (one-paragraph pitch, links to `docs/ideas.md`).
- Labels: `skill:<name>` created by `catalog.mjs --labels`, plus
  `bug`, `idea`, `skill-request`, `good first issue`.
- Discussions: enabled with GitHub's default categories. Category edits need
  GraphQL, which the session cannot call, so the owner renames in the UI.

## Scripts

All scripts: Node 22 ESM, no dependencies, `--help`, exit 1 on failure,
pure functions in `scripts/lib/` with `node --test` coverage.

| script | does |
| --- | --- |
| `new.mjs <name>` | creates `skills/<name>/SKILL.md` from the template, refuses an invalid name, runs catalog |
| `validate.mjs` | frontmatter rules above, directory/name match, body non-empty, stale versions |
| `catalog.mjs` | writes plugin.json, marketplace.json, README table, docs/index.html; `--check` for CI; `--bump`; `--labels` prints a `gh label create` script |
| `package.mjs` | writes `dist/` zips using the system `zip` |

## Testing

- `scripts/lib/*.test.mjs` — parse frontmatter, validate names, render
  catalog, deterministic output.
- Round trip: `catalog.mjs` twice yields identical files.
- A fixture skill under `scripts/lib/fixtures/` keeps tests independent of
  real skills.
